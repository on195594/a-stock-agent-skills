## 1. 本规范的定位与优先级

本规范将 2026-09-17 投资与架构审查转化为分阶段实施任务。它是针对当前实现的增量修订，不替代既有总纲、投资规则与生产安全约束，也不重新打开已完成的架构收敛项目。

规范阅读顺序为：**三仓总纲 → 当前架构 → 适用的专项规范 → 本轮实施任务 → 代码及验收证据**。既有规范与本规范发生实质冲突时，应列出冲突并取得裁决；不能自行宣布旧规则失效。

本次先后顺序固定为：

1. **S0：只读确认事实基线。** 区分远端代码、发布包、实际安装版本和生产证据。
2. **S1：修复 Agent 风险状态与复核路径。** 预算超限不得进入干净快速路径；缺失风险不得显示正常。
3. **S2：补齐 Tracker 证据资格与并列分数处理。** 保持生产评分不变，修正评估口径。
4. **S3：建设最小账户业绩闭环。** 复用交易账本，以可核实账户事实衡量净值、收益与回撤。
5. **S4：条件满足后开展下一轮投资实验。** 先简化基线、消融和可成交验证，再讨论扩张。

S1—S3 是有限的软件交付；S4 是有前置条件的研究任务，不能因前面测试通过而自动启动。S0 中生产环境暂不可访问，不阻止已具备源码证据的隔离开发，但必须保留生产未核实状态。

## 3. 目标与非目标

### 3.1 交付目标

本轮应使系统具备三个可核查的结果：

**风险结论一致。** 同一份有效输入，在 JSON、文本和 Skill 路由中不能同时出现“超预算”与“无事可做”。

**投资证据可裁决。** 报告可以区分“样本不足”“可以进行方向复核”和“尚未证明可实盘采用”，并解释具体缺口。

**账户表现可追踪。** 外部入金不被当作投资盈利，持仓生命周期收益不被当作账户收益，历史不足不被补造。

### 3.2 明确排除

本轮不增加股票池、不调整评分权重与 44 分阈值、不恢复在线模型每日打分、不增加新投资框架；不建设自动交易、券商下单或无人确认的再平衡。

本轮不引入微服务、消息总线、独立 Model Gateway、多 Agent 管理平台、MCP/A2A 基础设施、向量库、图数据库、全量 DDD 或第四个仓库；不将两个消费者的 SQLite 合并或互相开放直接写入。

本轮不宣称实现财富自由、稳定超额收益或最大回撤保证。用户历史表达的 5% 回撤偏好不能自动写成账户阈值；其适用资产范围与当前有效性尚需明确。

## 4. 架构决策

### 4.1 三仓职责保持不变

| 仓库 | 负责 | 不负责 |
|---|---|---|
| Tracker | 分配研究注意力；候选、信号快照、实验与研究评估 | 真实个人持仓、交易授权、账户预算裁决 |
| Agent Skills | 分配个人风险预算；决策、持仓、监控、账本、业绩和复盘 | 全市场选股基础设施、共享数据供应平台 |
| Lib | 可复用的确定性计算、数据适配、来源与时效语义 | 账户状态、L3/Tier 生命周期、Skill 编排 |

两个消费者分别依赖 lib，不相互导入内部实现。未来确需交接候选时，先使用带来源、时间与版本的静态数据，不新增常驻中间服务。[R3][R4]

### 4.2 共享计算不等于统一策略

Tracker 的生产评分和 lib 的 A—F report-only 基本面评分不能仅因同名就被强制合并。财务口径、估值纯函数及数据失败语义可以共享；不同策略的目标、分数含义和验证记录应保持明确身份。[R3][R9]

本轮默认不修改 lib 公共接口、不发布新 lib 版本。Agent 私有需求留在 Agent；只有已存在的跨消费者需求才构成上移理由。

### 4.3 版本身份不得混用

| 身份 | 用途 | 本轮处理 |
|---|---|---|
| build/package identity | 实际代码及依赖身份 | 如实记录，不冒充投资政策版本 |
| scoring/policy identity | 决定输入、评分与阈值的规则身份 | 不改变当前 Tracker 生产评分 |
| evaluation identity | 资格检查、分桶、收益和回撤评估口径 | S2 增加明确的评估版本标记 |
| wire contract identity | JSON 字段和语义约定 | 保留 `decision-v1` / `monitor-v1`，只做必要修正 |

Tracker 当前 hash 包含评分相关源码和 lib 版本，因此无关升级也可能切开 cohort。本轮不得为了版本号整齐而升级生产依赖；不得未经等价性证据合并历史 cohort。[R10]

这里只补显式身份与说明，不建设版本注册中心，不改造整套 hashing 机制。

## 5. S0：事实基线与部署差异核验

### 5.1 仓库基线

执行者应记录各仓库 HEAD、工作区状态、适用规范、依赖锁及现有检查命令。发现未知本地改动不得覆盖；不得用 `reset --hard`、清库或 force-push 获得“干净基线”。

若本地存在尚未 push 的修复，先比对差异与测试，不得因远端缺少该提交而重复实现。尤其应重新检查非法 `stop_reason` 的类型处理。

### 5.2 生产只读核验

获得合法的生产读取条件后，记录实际 CLI 路径、解释器、包版本、可取得的制品标识、现有客户端入口与已部署 Skill 身份。无需输出账号、token 或完整环境变量。

Tracker 核验重点是：首个完整新 hash 批次、预定 35 股覆盖、PB 物化来源日期、`scoring_snapshot_json` 和定性来源快照、行情与基准截止日。

不能删除当天记录重跑，不能执行会刷新数据、修改状态或隐含迁移的“检查命令”。只读命令也必须确认没有 schema bootstrap 或自动缓存写入副作用。

### 5.3 输出与退出条件

输出一份脱敏基线记录，分别标记 `REPOSITORY_VERIFIED`、`PRODUCTION_VERIFIED` 或 `PRODUCTION_NOT_VERIFIED`。此处状态仅用于本轮执行报告，不要求新增平台级状态模型。

生产不可访问时，记录原因和缺少的证据，继续可独立完成的源码与 fixture 工作；不得将生产状态写成已通过。

## 6. S1：Agent 风险闭环修复

### 6.1 RISK-01：预算超限必须进入复核

**现状。** `commands_monitor.py` 已计算 `account.risk_budget_status`，但后续 review/action/clean 判定没有使用该预算状态。数据完整且无其他升级项时，存在同时输出 `over_budget` 和 `clean_fast_gate` 的逻辑路径。[R5]

**修改要求。** 在既有快照构建流程中，将单股或组合预算超限加入 `escalations`。建议新增一个明确 reason code：`risk_budget_exceeded`，在合同词表、排序表、生产者、测试及 Skill 路由中一次性接通，不把它伪装成治理风险或行情异常。

单股超限的升级项使用股票代码；组合总风险超限的升级项允许 `code=null`。明细应给出风险金额、比例、适用限额、分母来源和超限范围。仅全组合升级时，Skill 应使用本快照汇总并加载组合风险 reference，不为全部股票重新做研究。

在“仅预算超限、数据完整”的隔离场景中，必须满足：

```text
account.risk_budget_status = over_budget
review_status              = review_required
action_status              = review_candidate
stop_reason                = null
requires_user_confirmation = false
manifest.writes            = false
```

`requires_user_confirmation=false` 仅表示当前是只读复核候选，绝不构成后续 W1 写入许可。

**动作边界。** 预算超限要求复核并阻止直接批准新增风险，不生成自动卖出，不下调止损线，不自动调整仓位，也不写入真实 alerts、L3、Tier 或账户状态。

如同时存在符合当前规则的减仓/退出候选，必须保留既有交易候选、数据门禁与用户确认要求，不能被新增的预算复核项降级覆盖。数据 stale/unavailable/conflicted 时保留既有 blocked 行为。不得借本修复改变 L3、流动性冲击或止损策略。

### 6.2 RISK-02：合同拒绝矛盾的干净路径

`monitor_contract.py` 增加交叉字段校验：`account.risk_budget_status=over_budget` 不能与 `review_status=cleared`、`action_status=no_action` 或 `stop_reason=clean_fast_gate` 并存。

有活动持仓时，生产者只有在预算可判定且未超限、现有数据和估值检查通过、无升级及缺口时，才能生成干净路径。缺分母、缺有效止损、缺必要价格等不能被解释为零风险。

无活动持仓且本地状态确实有效时，保留既有空仓快路径；数据库读取失败产生的空数组不能当作真实空仓。历史简化 fixture 与真实生产输出应区分，不能为迁就不完整 fixture 削弱生产校验。

保留 v1 合法附加字段兼容；不重命名字段、不重新抽取合同。不更改历史 Agent 证据来制造通过，应保留其来源版本并补充当前修复的独立证据。

### 6.3 RISK-03：旧文本入口不得将未知风险输出为正常

`commands_holdings.py::cmd_portfolio_risk()` 对无法计算 `stop_risk_pct` 的持仓，输出“风险不可完整判定”及缺失项，而不是落入“正常”。缺失金额不得加入合计作为零值。[R11]

能够计算的已知风险之和可保留为明确标识的下限；未覆盖全部有效持仓时，不能据此宣称组合在预算内。已破止损线仍应显示破线状态，即便公式中的剩余止损距离为零。

优先复用现有数值校验和小型纯函数，使相同有效输入得到一致的预算判断；不要再做一套文本专属阈值系统。需要修正只读入口的数据库会话时，只处理本入口；缺 schema 时报告不可用，不能自动迁移。

### 6.4 RISK-04：受控处理非法 stop_reason

对 `stop_reason` 先做类型检查，再做枚举判断。数组、对象、布尔值、数字及未知字符串统一抛出 `MonitorContractError`，不能泄漏 `TypeError`。合法值仍为 `null` 或 `clean_fast_gate`。[R12]

从 Python 对象验证和从 JSON 解析两条入口分别测试。非有限数值、附加字段兼容、manifest 写入限制等现有合同测试继续保留。

### 6.5 阈值策略与本轮边界

S1 保留当前单股 2%、组合 8% 的启发式默认值及现有 `>` 边界，不在修 bug 时悄悄调整投资政策；测试应覆盖恰好等于阈值的情况。报告必须标注这是适用政策参数，不是已验证的安全保证。

旧 CLI 的显式覆盖值必须显示其实际生效参数，不能与默认参数混为同一输入。统一个人政策配置放在 S3，小补丁不得被扩展为配置平台。

| 编号 | 输入场景 | 预期 |

## 7. S2：Tracker 投资证据与评估口径修复

### 7.1 EVAL-01：覆盖率分母来自预定股票池

当前报告从历史成功预测数的最大值推导 `expected_size`，可能把持续漏写后的数量当成完整股票池。[R13]

分母必须来自该实验版本事先确定的股票代码集合，而不是成功写入数量、可取价数量或当下仍留在池内的股票。

当前固定 35 股实验，优先使用可追溯到对应提交的股票池配置及其 hash；历史股票池无法证明时，该历史段只能用于诊断。不能拿今天的 watchlist 反推所有历史日期的预定名单。

本轮优先在现有报告层读取并输出实验股票池身份，不修改会影响评分 hash 的编排源码，不新增生产表。确实需要持久化实验身份时，使用仓库外的一份冻结实验元数据文件；它只记录实验配置，不复制 predictions，也不形成并行研究系统。

分别输出：预定数量、实际预测数量、快照合格数量、对齐收益样本数量和最终纳入名单。固定 35 股且覆盖门槛为 90% 时，至少需要 32 只；持续仅写入 30 只不能自我调整成合格。

### 7.2 EVAL-02：快照完整性不等于所有财务指标均非空

现有写入已包含 `scoring_snapshot_json`、`qualitative_snapshot_json`、`qualitative_sources_json`、`qualitative_mode`，应验证和复用，不创建另一套快照。[R14]

对修正后实验的资格校验至少包括：

- 记录的 code/date/framework/hash 与所属实验一致，重复或冲突记录不重复计数。
- 快照可解析为合法对象，无 NaN/Infinity；有实际评分输入、weights、result 和 implementation 身份。
- 快照 result 与落库分数在既有舍入规则下相符；缺失输入按照原评分政策明确记录。
- 定性分来源可解释：实际使用缓存时保留当时日期；明确使用 fallback 时允许相应日期为空，但不能把 fallback 描述成已核实的当日判断。
- 时间、来源与财报期间没有明显自相矛盾；无法证明的信息可得时间作为限制披露，不能把财报期末日冒充公告日。

**禁止把“快照完整”实现为“财务字段必须全部非空”。** 严格十年估值窗口导致的合法缺失，应按冻结评分政策处理；本轮不能因此改变评分算法或偷偷筛掉特定类型的公司。

旧记录没有当时快照时不得用最新缓存补造。历史重算使用当时的已记录实现身份，不能仅因当前安装包不同而宣布所有旧快照错误。

### 7.3 EVAL-03：证据资格与投资裁决分离

保留现有 30/60/90 自然日窗口、90% 截面覆盖与 3/2/1 个合格非重叠截面的数量门槛，除非另有明确授权改变实验协议。[R10][R13]

报告应分别给出机器可辨识的证据资格与缺口。以下为本轮建议语义，可在现有报告实现，不要求新增服务或通用合同：

```text
INSUFFICIENT_EVIDENCE
  关键来源、股票池、快照、价格/基准或成熟截面门槛未满足。

READY_FOR_DIRECTION_REVIEW
  已达到本实验方向复核所需条件；不代表统计显著、可交易或适合实盘。
```

每个窗口单独说明资格；总体只有在当前协议要求的窗口与数据条件均满足后才进入方向复核。不得仅凭截面数够了就输出“有效”。

行情新鲜度应依据适用的交易日与现有数据可用规则判断，不硬编码“必须等于今天”或用全库最大日期掩盖单股滞后。缺失收益样本须展示具体名单与原因，不能无声删除后改变分母。

诊断指标可以在不合格状态下显示，但须紧邻标注“仅诊断，不参与本轮裁决”。不合格状态不能仅藏在页脚免责声明中。

### 7.4 EVAL-04：Q5/Q1 不得由股票代码决定

当前读取先按日期、代码排序，再按分数稳定排序截取两端，因此分桶边界的并列分数可能保留代码顺序。IC 已有并列平均秩处理，应保留，不要重复修错位置。[R13]

采用一个共享的纯函数产生分桶权重，并由 spread、Q5 路径和逐日回撤共同消费，禁止三个计算入口各自取 Top-K。

推荐本轮固定的处理规则：设截面有 n 只，k=max(1, floor(n/5))；严格优于边界分数的 m 只各占 1/k，边界同分组共 g 只，则各自权重为：

```text
(k - m) / (g × k)
```

Q1 对称处理。权重之和为 1；不得使用股票代码、未来收益或随机种子打破并列。

权重在评分截面确定后固定，日间净值沿用期初权重乘以各股累计价格比的组合，不变成每日再平衡策略。先用当时可用的评分确定候选与权重，再检查收益数据；未来行情缺失不得导致重新排名、用其他股票补位或对剩余股票重新归一化。正权重成员缺必要行情时，该篮子的完整收益/回撤不可用，不能用90%截面门槛掩盖。

全截面同分时标记 `ALL_SCORES_TIED`：IC 和排序优势指标为 N/A，Q5 策略结论不可用；观察池等权和基准收益仍可作为描述性信息。仅部分边界同分时，披露并列数量和分摊规则；两端因大并列组出现重叠也必须披露，不能伪装成完全分离的组合。

全同分是已经观察到的无区分能力事实，不应被无限解释为“继续等待更成熟样本”。数据资格完整时仍可进入方向复核，但不得产生虚构的排序收益证据。

这是评估口径修正，不修改历史分数，不倒填新的股票选择。报告增加 `evaluation_version`，保留此前结果的版本标签；不得把新旧分桶结果拼成一个未注明变化的绩效序列。

## 8. S3：个人政策与最小账户业绩闭环

### 8.1 POLICY-01：统一有效风险参数

在 S1 稳定后，为 Agent 增加一个小型个人政策配置，存放于现有仓库外配置目录。复用既有配置设施，不新增配置服务。

第一版仅需记录适用账户/资产范围、币种、有效时间、政策身份、单股与组合止损风险限额、用户确认状态，以及可选的回撤观察目标。分母金额与日期仍应作为本次有效账户事实提供，不把过期静态金额当作实时资产。

参数优先级固定为：明确的本次 CLI 参数 → 已确认有效配置 → 明确标注的兼容默认值。非法配置不得静默回退成默认值；不同入口必须展示相同的最终生效参数与来源。

5% 历史回撤偏好只作为待确认背景，不填入生产配置。兼容默认值不是用户确认政策，也不是安全保证。

“到止损线的估算损失”“账户历史最大回撤”“假设情景损失”分别显示；本轮不增加自动优化仓位，不承诺任何未来回撤上限。

### 8.2 PERF-01：先做只读、单账户、人民币 MVP

本轮第一版仅支持一个明确账户、一种币种、已核实的日终账户事实。多币种、家庭全部资产、衍生品、融资融券和自动券商同步暂不纳入；数据超出范围时明确拒绝混算。

账户范围是软件 MVP 边界，不是对用户应持有什么资产的建议。

默认采用**只读文件输入 + 现有账本对照 + 一份业绩输出**，暂不增加生产数据库表或 cron。该选择避免业绩建设一开始就变成迁移项目。

如后续确需自动持久化净值或引入新 schema，必须另行明确授权并单独设计迁移与回滚，不能捆绑在本轮修复内执行。[R15]

### 8.3 事实来源与最小输入

现有交易事件账本仍是已记录买卖、费用、分红及持仓生命周期的来源；不导入第二套买卖流水，不重建持仓表。

新增的账户输入文件只承载账本尚不足以完整表达的**账户级资产快照与外部入出金**。建议一行对应一个日终估值，至少包含：

| 字段 | 含义 |
|---|---|
| valuation_at | 带时区的估值时间；A股日界线按 Asia/Shanghai，不跟随客户端所在时区 |
| currency / account_scope | 币种及受评估账户范围 |
| total_equity / cash | 已核实的账户总资产与现金；明确负债、应收应付的口径 |
| external_inflow / external_outflow | 外部入金/出金分别记录，非负金额 |
| flow_timing | 无外部流、已确认期末发生、仅按期末假设、或不支持 |
| source_ref / reconciliation_status | 脱敏来源及与既有持仓/现金事实的核对状态 |

具体字段名在实施时与现有接口风格对齐，但上述语义不可省略。货币输入拒绝 NaN/Infinity；使用十进制定点解析或等价的明确精度方案，输出保留币种与精度。

文件放在现有 state 目录的专用子目录，原始事实输入与生成的 artifacts 分开保存，不进入 Git；权限限制、备份与脱敏沿用现有操作规范。此文件不是第二份交易账本，也不得写回覆盖现有持仓。

账户净值优先依据可核实的券商账户快照；现有事件账本用于对照解释，不对历史缺失交易进行自动推断。若两者不一致，先标记差异，不用虚构现金流把账对平。

### 8.4 PERF-02：收益、净值与现金流公式

现有生命周期 `盈亏 / 累计买入投入` 保持原义，不更名为账户时间加权收益。[R6]

账户级收益需要剔除外部入出金。分红、利息是投资收益而不是外部入金；费用及税费应体现在账户表现中，不可重复扣减。时间加权收益的目标是尽量中和外部现金流的影响，子期间应几何链接；本工具只借鉴业绩计量原则，不宣称符合整套 GIPS 要求。[R16]

第一版固定使用以下受限口径：没有外部现金流，或现金流已确认在该日终估值前的期末边界发生时，令 Vt 为期末流后总资产，Vt-1 为前一期流后总资产，Ft 为净外部流入，则：

```text
rt = (Vt - Ft) / Vt-1 - 1
Nt = Nt-1 × (1 + rt)       # 归一化业绩净值，从1起算
DDt = Nt / max(N0...Nt) - 1
MDD = min(DDt)
```

以上公式的时点假设必须写入输出。期初或盘中现金流不能无条件套用该公式；只有日终事实且缺少现金流时点时，可以在显式选择假设后输出“日终现金流假设下的近似收益”，不得标成精确 TWR。

无法合理识别现金流、估值或账户范围时，不发布该期间的可比收益及完整区间 MDD。不跨数据缺口无声拼接；从下一个可核实起点重新建立区间，并保留缺口说明。

本金为零、负资产、清空后重新入金等超出第一版算法定义的区间，返回不可计算或开启新的明确区间，不能除以零或无限年化。

**自检例子。** 前一期资产100，投资收益10，期末入金50，则期末资产160，收益为10%，而不是60%；随后期末出金10、资产150，若没有投资盈亏，则该期收益为0%。这些仅为算法 fixture，不是用户资产数据。

使用实际持股数和账户市值时，不可再用前复权价格加现金分红，避免重复计入公司行动收益。来源已经计入费用或税费时不得再次扣减。

### 8.5 PERF-03：基准与输出

第一版基准通过一份可追溯的日终基准输入文件提供，不新增联网采集链。用户选择的基准及组合权重必须事先确定并记录有效时间，不能根据事后表现挑一个更容易跑赢的比较对象。

沪深300全收益可作为权益参考，但不自动成为低权益或含大量现金账户的唯一比较基准。基准缺失只阻断相对比较，不阻断可独立成立的账户绝对收益计算。

对齐币种、期间和估值日期。报告应区分指数参考与可执行替代方案，不把忽略费用的指数结果说成实际可取得的净收益。不改变现有决策授权，只输出：

**账户范围与数据覆盖 → 现金流及计量方法 → 账户收益与净值回撤 → 同期基准和差额 → 未解决的数据问题。**

第一版不提供 XIRR、多因子归因、收益预测或 AI 收益贡献百分比。报告变好不证明 AI 带来因果性超额收益。

## 9. S4：下一轮投资实验的启动条件

当前修正版本首先完成既有方向复核。原 2026-09-20 / 2026-09-23 检查日期不适用于新版本，不设一个无数据支持的新“最终有效性日期”。[R10]

达到方向复核门槛，也不等于通过实盘采用门槛。是否继续、简化、重做或停止，应沿用当前有效的预注册协议；不根据真实持仓盈亏或单只股票表现替代裁决。

下一轮建议顺序为：简单排序基线 → 去定性分等有限消融 → 行业内比较 → 明确策略对象的可成交验证。每个实验开始前冻结假设、样本、指标和终止条件，不同时搜索大量权重后只保留赢家。

可成交验证必须分别定义 Q5 和 ≥44 分名单，至少说明信号可用时间、最早允许成交时点、进出规则、费用与滑点、无法成交和缺数据处理。交易约束按实施时的交易所及数据提供方原始资料确认，本文不硬编码可能变化的市场规则。

不以更强模型重写旧定性分，不把后见信息加入当时输入，不将费用前研究收益直接宣传为个人账户可实现收益。

**S4 本轮状态：DEFERRED / CONDITIONAL。** 未满足条件时，只记录下一次需要读取的证据，不偷偷启动股票池扩张或参数优化。

## 10. 总纲与文档收敛

在 Agent 的 `docs/architecture/a-stock-ecosystem-charter.md` 放置唯一三仓总纲。实施前先检查用户已有获批总纲及仓库最新内容；存在时做最小补充，不重写；尚未落库时取得正确原文，不根据标题补造“已批准版本”。

Tracker 和 lib 只增加指针，不复制全文。总纲主要记录三仓职责、依赖方向、投资证据边界、禁止事项和真实账户所有权；不扩写成制度手册。

Tracker 路线图中的仓位、退出与风险预算，应明确区分“策略模拟规则”和“真实个人账户管理”。前者可以研究，后者由 Agent 持有唯一应用责任。[R10]

必要文档更新限定为现有 README/索引、runtime contracts、操作说明及相应测试证据。日常 Skill 上下文只保留路由和当前规则，不自动加载全部历史 spec、评审或迁移记录。

## 12. 测试与证据要求

Agent 以仓库当前 `scripts/check.sh` 和既有独立 QA、cron fixture、合同及 Agent 行为检查为准；Tracker 以当前 pytest、Ruff、format、mypy 及结构检查为准。执行前读取实际脚本，确认只使用隔离数据与禁用通知配置，不盲跑历史文档中的生产命令。[R7][R8][R15]

lib 未修改则记录所消费版本与相关回归范围，不为形式完整强行改包。涉及合同枚举更新时，必须验证所有已知消费者，不能只通过生产者单元测试。

证据最少包含：被验证提交、命令、退出码、测试摘要、未执行项和原因，以及是否使用真实数据/真实模型/网络。假工具场景与真实客户端运行必须分别标注。

测试或报告生成不得泄漏凭证、账户详情、生产数据库、WAL/SHM 文件或未脱敏日志。fixture 使用合成事实，不将真实账户复制进仓库。

本轮不能用以下内容作为完成证明：未经运行的预期数字；过去的测试计数；只更新快照后得到的全绿；仅有文档“已完成”标记；仅有 CI 而无关键缺陷的定向回归。

## 13. 安全、生产授权与回滚

### 13.1 授权不可跨范围继承

| 行为 | 本文是否已授权 | 后续边界 |
|---|---|---|
| 编制本规范 | 是 | 当前请求 |
| 修改、提交并push代码 | 否 | 用户明确实施后，按master直接提交规则 |
| 只读获取生产事实 | 不假定已有访问 | 使用合法访问，确认没有隐式写入 |
| 更改生产schema、cron、客户端入口 | 否 | 单独明确授权，独立验收与回滚 |
| 改评分、股票池、投资阈值 | 否 | 明确有日期的策略规范与用户授权 |
| 真实W1状态写入 | 否 | 用户确认具体动作，并使用全局confirm-write门禁 |
| 自动下单或自动交易 | 否 | 本规范不建设该能力 |

历史规范的 `AUTHORIZED FOR IMPLEMENTATION` 不能自动授权本轮新增策略或生产变更。用户批准某一阶段，也不等于批准所有后续条件实验。[R15]

### 13.2 回滚策略

代码使用小提交和 `git revert` 保留历史，不重写 master。部署回滚使用已记录的不可变制品和对应 Skill；涉及新增 reason code 时生产者与消费者成组回滚，避免一端不认识枚举。

Tracker 保留原始预测不变。评估逻辑回滚时保留各自 `evaluation_version` 与报告说明；不能把退回旧实现说成统计口径没有变化。

S3 MVP 不迁移数据库，回滚仅撤销相关代码/入口，保留并保护用户事实输入；不得删除用户账本、原始账户快照或为了回滚制造反向交易。

## 14. 总体验收与实施回执

本轮不能只有一个笼统的“完成”。每阶段应分别标记实现、测试、生产和投资证据状态。允许软件修复完成、生产未部署、策略仍证据不足同时成立。

总体验收要求为：

- 风险超限或未知风险不再被伪装成无动作；已有安全门禁不退化。
- Tracker 的证据资格可解释，并列分桶与回撤口径一致，不改变冻结评分。
- 账户业绩MVP区分现金流与收益，数据不足不补造，未声称AI因果性收益。
- 三仓边界保持清晰，未增加不必要平台、仓库或常驻服务。

执行结束必须提供以下回执，逐项如实填写：

```text
Overall status:
  各阶段状态；不要把implemented写成deployed或investment-validated。

Repository heads:
  修改前/后的各仓库SHA；未修改仓库也说明。

Completed:
  条目ID、实际变化、对应证据。

Not completed:
  条目ID、原因、缺少的事实/授权/数据；条件实验明确为deferred。

Tests:
  命令、环境、退出码、通过/失败/跳过；未运行项不可省略。

Security/production impact:
  是否访问生产、是否联网、是否修改schema/cron/客户端/W1、是否发通知。

Rollback:
  可回退提交/制品、数据保留方式及生产者/消费者兼容要求。
```
